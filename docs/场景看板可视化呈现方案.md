# 场景看板可视化呈现方案（专项）

> 版本：v1.1　|　日期：2026-08-19　|　产品：中海言析智能工作台　|　落地载体：`web/index.html`（网页端 / 桌面端 Electron 同源）
> v1.1 修订：复看自审 8 处实质问题（单文件无构建约束、SVG token 实现方式、响应式与更多+冲突、spec 向后兼容、动态更新后端架构冲突、Phase 2 工期重估、agent 产出兜底、性能过度设计），见第 5 节。
> 结论先行：场景看板已是产品核心能力。当前（BUILD_TAG 1808）已具备「SVG 柱/折/饼 + marked 图文混排 + 2×3 宫格 + 预览层」的最小可用闭环，但仍停留在**工具级**——配色硬编码、无主题、无动画、无响应式断点、boardView 是静态文本快照、不可配置。本方案从**技术实现**与**产品能力结构**两个维度，给出可渐进落地的升级路径，目标把看板从「能看」升级为「美观、可配、可演进」。

## 0. 现状基线（基于代码实测）

当前可视化相关实现集中在 `web/index.html`：

| 能力层 | 现状实现 | 状态 |
|---|---|---|
| 图表渲染 | 手写 SVG：`renderBarChart` / `renderLineChart` / `renderPieChart`，`viewBox` 自适应，`max-width:420` | ✅ 可用，0 依赖 |
| 内容解析 | `renderBoardContent`：正则拆 ` ```chart ` JSON 块→SVG，其余走 `marked` 渲染文字 | ✅ 图文混排 |
| 宫格缩略 | `miniVizCard`：有 chart 块→画首图缩略；无→文本截断；无 boardView→状态色条 | ✅ 可用 |
| 预览层 | `openScenePreview`：右侧抽屉单栏渲染 `renderBoardContent` 结果 | ✅ 可用 |
| 布局 | 宫格 `kv-grid` 固定 `repeat(3,1fr)`；列表视图 `cardHtml` | ✅ 固定 3 列 |
| 主题配色 | 柱图单蓝 `#378ADD`、折线绿 `#1D9E75`、饼图 8 色硬编码数组 | ⚠️ 硬编码，无 token |
| 动画交互 | 无动画；卡片仅 `data-act="preview"` 点击 | ⚠️ 无 hover/入场/tooltip |
| 响应式 | SVG `width:100%`；宫格固定 3 列，无断点 | ⚠️ 仅 SVG 自适应 |
| 数据绑定 | `boardView = {type,data:{text}}` 静态快照（对话回写 / 定时任务发布） | ⚠️ 无动态更新 |
| 配置能力 | 图表由 agent 产出 JSON 决定，用户不可改 | ⚠️ 不可配置 |

**现状 7 项核心短板**

1. **缺主题系统**：配色硬编码，无法切换浅/深主题，无法注入品牌色，与全局设计 token（`#F7F7F8`/`#18191C`）未打通。
2. **图表表现力弱**：无坐标轴/网格线/刻度、无图例（柱/折线缺）、无 tooltip、无数据标签对齐、饼图标签易溢出。
3. **无动画**：图表静态出现，无 hover 高亮、无入场、无加载态，质感偏「工具」而非「产品」。
4. **响应式缺失**：宫格固定 3 列，平板/手机下拥挤；预览层抽屉移动端未全屏。
5. **boardView 是文本快照**：依赖 agent 在 markdown 内嵌 ` ```chart `，不稳定、不可控、用户无法改图表。
6. **不可配置**：用户不能选图表类型、配色、字段映射、布局密度。
7. **无动态更新**：定时任务发布是一次性快照（P4），不支持订阅刷新。

## 1. 技术实现方案（多维路径对比）

### 1.1 图表渲染方式

| 路径 | 包体 / 依赖 | 优势 | 局限 | 适用场景 |
|---|---|---|---|---|
| **A. 手写 SVG（现状）** | 0 依赖，原生 | 极致轻量、完全可控、易与现有 `renderChart` 衔接、无构建负担 | 需自己画坐标轴/网格/tooltip；复杂图表（雷达/地图/漏斗）成本高；交互需手写 | MVP / 轻量看板 / 离线优先 / 内网受限环境 ✅ **当前推荐基线** |
| **B. ECharts** | ~1MB（全量）/ 可按需引入 ~300KB | 图表类型最全（50+）、交互强（缩放/刷选/tooltip）、主题完善、文档好 | 包体大；canvas 渲染在纯静态导出/无障碍上弱；定制深度样式需熟悉 option | 富图表看板、大屏、需钻取/联动的中期目标 ✅ **中期推荐** |
| **C. AntV G2Plot** | ~500KB | 语义化「图表即配置」、默认美观、图表类型覆盖运营场景（柱/折/饼/雷达/漏斗） | 深度定制不及 D3；与现有 SVG 体系差异大需重构 | 偏运营分析、追求「开箱美观」的中期目标 |
| **D. Chart.js** | ~200KB（canvas） | 轻量、动画开箱即用、API 简单、社区大 | 图表类型中等；复杂定制弱；canvas 不利于 SEO/导出 | 轻-中型看板、重视动画但无需深度定制 |
| **E. D3.js** | ~280KB | 极致自由，任意可视化（力导/地理/自定义） | 学习曲线陡、开发慢、需自己搭交互 | 特殊可视化（关系网络/地图钻取）等长尾场景 |
| **F. Canvas 自绘（无库）** | 0 依赖 | 大数据量（万点）性能好 | 全部手写、成本高、无现成交互 | 超大数据集监控，非常规看板 |

**建议**：短期保留路径 A 并增强（补坐标轴/网格/图例/tooltip）；中期引入 **B（ECharts）或 C（G2Plot）作为「富图表引擎」**，保留 A 作轻量兜底与离线场景。用 `boardView.spec.engine` 字段区分渲染器，平滑过渡。

> ⚠️ **架构约束（v1.1 修正）**：`web/index.html` 是**单文件、无构建链**（直接 `<script>` 引 UMD），"按需引入 ~300KB"需要 tree-shaking 构建，当前架构不成立。中期引富图表只能引**全量 UMD**（ECharts ~1MB / G2Plot ~500KB），且桌面端 Electron `file://` 加载**必须本地内联**（CDN 在离线/内网不可用）。结论：中期升级需同步评估"是否值得引全量库"vs"继续增强 SVG"，而非默认按需引入。

### 1.2 布局引擎选择

| 路径 | 优势 | 局限 | 适用 |
|---|---|---|---|
| **CSS Grid（现状宫格）** | 原生、无依赖、`repeat(3,1fr)` 简洁 | 固定列数；自定义拖拽需额外 JS | 固定 2×3 宫格 ✅ 当前 |
| **Flex + 自动换行** | 简单、卡片自适应流式 | 难做等高对齐、拖拽编排 | 列表/流式卡片 |
| **Masonry（瀑布流）** | 错落排布、信息密度高、图卡混排美观 | 实现复杂（列高计算）；顺序感弱 | 卡片高度差异大的看板墙 |
| **Gridstack.js（拖拽网格）** | 用户可拖拽/缩放/跨列编排；存 layout JSON | 引入依赖（~50KB）；需 layout 数据模型 | **用户自定义布局编排**（中期）✅ |
| **CSS 容器查询（@container）** | 卡片随自身尺寸而非视口响应，组件级响应式 | 兼容性需评估（现代浏览器已支持） | 组件自适应 ✅ 推荐引入 |

**建议**：宫格继续保持 CSS Grid；引入 `@container` 做卡片级响应式；中期自定义编排用 Gridstack，layout 存 `scene.layout`。

### 1.3 主题与配色体系

现状配色硬编码在 `renderBarChart`（单蓝）、`renderPieChart`（8 色数组）。需升级为**语义化设计 token**：

```
--viz-primary:    #378ADD;  /* 主数据色（柱/主系列） */
--viz-positive:   #1D9E75;  /* 正向/增长（折线/达标） */
--viz-warning:    #BA7517;  /* 预警/进行中 */
--viz-negative:   #D4537E;  /* 负向/风险 */
--viz-categorical: #378ADD #1D9E75 #BA7517 #D4537E #534AB7 #639922 #E24B4A #888780; /* 分类色阶（饼/多系列） */
--viz-grid:       #ECECEC;  /* 网格线 */
--viz-axis:       #9CA3AF;  /* 坐标轴/标签 */
--viz-surface:    #FAFAFA;  /* 图表卡底 */
```

- **构建方式**：全部走 CSS 变量（`:root` + `[data-theme="dark"]`），与全局 token（`--text`、`--border`、`--bg`）同源。
- **浅/深主题**：预览层与宫格套 `data-theme`。
- ⚠️ **SVG token 实现方式（v1.1 修正）**：SVG **属性** `fill="var(--x)"` 不生效，必须用 `style="fill:var(--viz-primary)"` **内联样式**或 CSS 类选择器（`.bar-series-0 { fill: var(--viz-primary) }`）。现状 `renderBarChart` 是 `fill="#378ADD"` 属性硬编码，token 化时需把所有 fill/stroke 改为 style 或类。
- **品牌注入**：运营类看板可覆盖 `--viz-primary` 为企业色。
- **无障碍**：分类色阶需满足对比度（避免红绿盲不可分，关键区分加图案/标签）。

### 1.4 动画与交互

| 手段 | 实现 | 适用 |
|---|---|---|
| **CSS transition（hover）** | 卡片 `:hover` 抬升 + 阴影 + 边框聚焦色 | 宫格卡 ✅ 立即可做 |
| **SVG 描边动画** | 折线 `stroke-dasharray` 绘入；柱 `height` 从 0 升起（CSS `@keyframes`） | 入场质感 ✅ 低成本 |
| **入场淡入** | `IntersectionObserver` + `opacity/translateY` 过渡，滚动进入视口时渐显 | 宫格/长列表 ✅ |
| **Tooltip** | 鼠标 `mouseover` 柱/点→绝对定位浮层显示数值+标签 | 精确读数 ✅ 中期 |
| **骨架屏** | 数据加载时 SVG 占位脉冲，避免空白跳变 | 动态更新场景 |
| **JS 动画库（GSAP / anime.js）** | 复杂时序/路径动画 | 大屏/特殊叙事，常规看板不必引入 |

**建议**：短期用纯 CSS（hover + 入场 + 柱升起）即可显著提质，零依赖；tooltip 随 ECharts/G2Plot 引入自然获得。

### 1.5 响应式适配

| 断点 | 宫格列 | 预览层 | 图表处理 |
|---|---|---|---|
| 桌面 ≥1280 | 3 列 | 右侧抽屉 640px | 完整 |
| 平板 768–1279 | 2 列 | 抽屉 520px 或模态 | 标签旋转/缩排 |
| 手机 <768 | 1 列（可横滑） | **全屏模态** | 横轴标签 45° 或省略，图例置底 |

- SVG 已 `width:100%` + `preserveAspectRatio`，天然缩放；补 `@container` 让卡片内图表随卡片宽而非视口变。
- 预览层 `@media (max-width:768px)` 改 `full-screen` 模态。
- ⚠️ **与"更多+"逻辑冲突（v1.1 修正）**：现状宫格固定 2 行 3 列、第 6 格恒为"更多+"（P6：top5 + 更多+）。响应式到 2 列/1 列后，"更多+"的位置与数量需重设计：建议 2 列时保持"末位更多+"（4 卡 + 更多+）；1 列时取消固定更多+、改为底部"查看全部"链接，避免纵向 5 卡 + 更多+ 的割裂体验。

### 1.6 性能优化

| 手段 | 说明 | 适用 |
|---|---|---|
| **懒渲染** | `IntersectionObserver` 仅渲染进入视口的图表 | 场景多（>20）✅ |
| **DOM 虚拟化** | 长列表用 windowing（只渲染可视区卡片） | 列表视图超长 |
| **SVG vs Canvas** | 数据点 <500 用 SVG（可访问/易导出）；>2000 用 Canvas/WebGL | 大数据监控 |
| **渲染缓存** | 同 spec 不重复解析；`marked` 结果 memo | 频繁重绘 |
| **CSS containment** | `contain: layout paint` 隔离卡片重排 | 宫格卡 ✅ |
| **防抖重绘** | 窗口 resize / 数据更新防抖 | 响应式 + 动态 |

> ⚠️ **当前规模不适用（v1.1 修正）**：现状场景数是个位数、数据点 <50，懒渲染/虚拟化/Canvas 大数据是**远超当前规模的过度设计**。这些手段**预留**到场景 >20 或数据点 >2000 再启用；当前只需 `contain: layout paint`（零成本）即可。避免为不存在的性能问题提前优化。

## 2. 产品能力结构调整方案

### 2.1 看板组件体系（分层）

```
看板容器 (KanbanBoard)
 ├─ 业务类型维度条 (BizTypeTabs)         [全部 / 存量运营 / +]
 └─ 场景区 (SceneZone)
      ├─ 宫格视图 (GridZone)   → 场景卡 ×5 + 更多+
      └─ 列表视图 (ListZone)   → 场景卡（紧凑）
           └─ 场景卡 (SceneCard)
                ├─ 可视化区 (VizZone)  → 可视化组件
                ├─ 标题/状态/业务类型 (CardMeta)
                └─ 操作 (预览/编辑/删除)
                     └─ 可视化组件 (VizWidget)
                          ├─ 图表 (ChartWidget: bar/line/pie/radar/…)
                          ├─ 指标卡 (MetricWidget: 大数+同比)
                          ├─ 进度条 (ProgressWidget)
                          ├─ 表格 (TableWidget)
                          └─ 富文本 (RichTextWidget: marked)
                               └─ 原子元素 (Title/Legend/Tooltip/Axis/Label/Tag)
```

**组件清单**

| 组件 | 职责 | 现状 |
|---|---|---|
| KanbanBoard | 容器 + 维度过滤 | ✅ |
| SceneCard | 场景入口卡 | ✅（kv-card） |
| ChartWidget | 图表渲染（按 engine 分派） | ⚠️ 仅 SVG 三型 |
| MetricWidget | 大数字指标卡 | ❌ 缺 |
| TableWidget | 结构化表格 | ❌ 缺 |
| RichTextWidget | 文字解读 | ✅ marked |
| LayoutEngine | 宫格/列表/自定义网格 | ⚠️ 仅宫格+列表 |

### 2.2 可视化元素配置能力

将 `boardView` 从「文本快照」升级为**结构化可视化 spec**：

```json
{
  "engine": "svg | echarts",
  "theme": "light | dark | brand",
  "widgets": [
    { "type": "metric", "title": "总份额", "value": 38.2, "unit": "%", "delta": +2.1 },
    { "type": "bar", "title": "各地市份额",
      "data": { "labels": ["西安","宝鸡","…"], "values": [42, 18, …] },
      "config": { "color": "primary", "showValue": true, "stack": false } },
    { "type": "pie", "title": "渠道占比",
      "data": { "labels": ["移动","联通","电信"], "values": [55, 28, 17] },
      "config": { "palette": "categorical", "showPercent": true } },
    { "type": "richtext", "content": "## 结论\n西安份额领先，但增速放缓…" }
  ]
}
```

- **类型库**：metric / bar / line / pie / radar / funnel / progress / table / richtext（可扩展）。
- **每元素可配置**：标题、数据源字段映射（`data.labels/values`）、配色方案、标签格式、阈值线、单位、是否显示数值。
- **配置存放**：存 `scene.boardView.spec`；agent 产出仍走 ` ```chart `，但新增「可视化编辑器」让用户事后调整（类型/配色/字段）。
- ⚠️ **向后兼容（v1.1 修正）**：现有 boardView 是 `{type,data:{text}}` 文本格式。升级 spec 后 `renderBoardContent` 必须同时识别两种形态——`boardView.spec` 优先，无 spec 时回退 `boardView.data.text`（旧数据不破坏）。迁移策略：旧数据按需升级（用户编辑时转 spec），不做一次性全量迁移。
- ⚠️ **agent 产出兜底（v1.1 修正）**：现状依赖智谱 GLM 按 prompt 产 ` ```chart ` 块，本身不稳定。需补：① 产出后 schema 校验（type/values 合法性），非法块降级为纯文本不报错；② 编辑器支持"从文本提取"手动补 spec；③ prompt 加 few-shot 示例提高产出率。

### 2.3 模板与布局编排机制

**模板来源（与 P3 对齐，三类）**
- 系统预设：运营日报、份额分析、趋势监控、风险看板。
- 用户保存：把当前 spec 存为「我的模板」。
- 看板库派生：直接选场景作模板。

**布局编排三档**

| 档位 | 说明 | 存储 | 适用 |
|---|---|---|---|
| 固定宫格（现状） | 2×3 自动排 | 无需 | MVP ✅ |
| 流式 Masonry | 错落自适应 | 无需 | 卡片异构 |
| **自定义网格** | 拖拽/缩放/跨列 | `scene.layout` JSON | 高级用户 ✅ 中期 |

**模板结构**：`{ id, name, layout:"grid|masonry|custom", widgets:[...], theme, bizType }`。

### 2.4 数据绑定与动态更新

| 阶段 | 数据形态 | 更新方式 |
|---|---|---|
| 现状 | 文本快照 `boardView.data.text` | 手动回写（对话/发布） |
| 短期 | 结构化 `boardView.spec` | 回写 + 版本（publishVersion 已有） |
| **中期** | spec + `sourceRef` 绑定源 | 定时任务发布支持「**持续订阅刷新**」（P4 当前是快照）→ 轮询/WebSocket 增量更新；卡片角标显示「实时/快照」 |

- ⚠️ **后端架构冲突（v1.1 修正）**：产品现状是"前端 js-sdk 直连共享 PG（rdb）+ **无自建后端推送**"。WebSocket 需要 CloudRun 常驻服务，与现有"无后端"架构冲突；轮询 rdb 可行但 RLS 下只能查自己 uid 行，定时任务结果要跨场景/跨用户共享需独立表 + 权限设计。
- **务实路径**：真订阅刷新列为远期（需新增 CloudRun 服务）。近期用「定时任务发布 = 更新发布」（publishVersion+1 已有）模拟"刷新"——用户手动/定时重跑任务→覆盖 boardView，看板显示最新版本；卡片角标标"快照 vN"。这避免引入后端推送，复用现有链路。
- 版本：`publishVersion` 已具备，支持「更新发布」覆盖。

### 2.5 用户自定义扩展能力

| 能力 | 说明 | 落地建议 |
|---|---|---|
| 自定义主题 | 切换浅/深、覆盖品牌色 | CSS 变量 + `data-theme` ✅ 短期 |
| 图表元素增删 | 在可视化编辑器加/删 widget | 中期（spec 编辑 UI） |
| 配色方案切换 | 分类色阶/单色系 | 中期 |
| 数据源扩展 | 当前 Excel 抽取；未来接 API/数据库/CSV 上传 | 中期 |
| 卡片样式 | 封面图/图标/强调色/业务类型色点 | 中期 |
| 开放 Widget | 高级用户写 chart spec 注册 | 远期（低代码） |

## 3. 落地演进路线图

| Phase | 目标 | 关键改动 | 工期 | 准出 |
|---|---|---|---|---|
| **Phase 1（近期·复用现状）** | 提质不重构 | SVG 增强（坐标轴/网格/图例/tooltip 占位）、设计 token 化、hover+入场动画、响应式断点（3/2/1 列 + 预览层全屏 + 更多+重设计）、`contain` 性能 | 3d | 宫格/预览层美观度达标、移动端可用、无新依赖 |
| **Phase 2a（中期·结构）** | spec 化 + 富图表评估 | `boardView.spec` 结构化（双形态兼容）、评估引全量 ECharts UMD vs 继续增强 SVG、schema 校验 + agent 产出兜底 | 3d | spec 落地、旧数据兼容、产出兜底可用 |
| **Phase 2b（中期·编排）** | 可配可编排 | 可视化编辑器（类型/配色/字段）、模板库、Gridstack 自定义布局、Metric/Table widget | 4d | 用户可改图表、可存模板、可拖拽编排 |
| **Phase 3（远期·动态）** | 活数据（需后端） | 近期先用"更新发布"模拟刷新；真订阅刷新需新增 CloudRun 服务（轮询/WS）单独评估 | 待评估 | 看板可刷新（模拟版立即可用） |

> Phase 1 与现有架构完全兼容（仍是 SVG + CSS），风险最低，建议优先落地。Phase 2 拆为 2a/2b：先结构（spec+兼容+兜底）后编排（编辑器+模板+拖拽），编辑器单独一期避免低估。Phase 2a 引图表库需评估"全量 UMD 包体"vs"继续 SVG"——桌面端 Electron 可内联打包不受影响，但网页端首屏 +1MB 需权衡。Phase 3 真订阅与"无后端"架构冲突，明确推后，不与看板美化耦合。

## 4. 推荐决策与结语

**短期（立即可做，零依赖）**：在现状 SVG 基础上做「提质四件套」——① 配色 token 化打通全局主题；② 补坐标轴/网格/图例让图表读得懂；③ hover 抬升 + 入场淡入 + 柱升起动画；④ 响应式断点（桌面 3 / 平板 2 / 手机 1 + 预览层全屏）。这能把看板从「工具感」拉到「产品感」，且不引入任何新依赖、不破坏现有 ` ```chart ` 协议。

**中期（结构升级）**：把 `boardView` 从文本快照升级为结构化 `spec`，引入 ECharts/G2Plot 富图表引擎 + 可视化编辑器 + 模板库 + 自定义网格。这一步让看板「可配置、可编排」，对应需求中「灵活支持多样化可视化」。

**远期（活数据）**：订阅刷新 + 多源接入，让看板从「结果快照」变成「实时面板」。

整套方案以现状代码为锚点、分阶段可落地，兼顾美观（token+动画+图表表现）、可用（响应式+tooltip+可配）、可维护（spec 结构化+组件分层+零/低依赖演进）。

## 5. 自审 v1.1 优化点与推荐落地方式

### 5.1 复看发现的 8 处实质问题

| # | 问题 | v1.0 偏差 | v1.1 修正 |
|---|---|---|---|
| 1 | 包体评估脱离单文件无构建现实 | 写"按需引入 ~300KB" | 单文件无 tree-shaking，中期只能引全量 UMD；桌面端 file:// 必须本地内联；需重新评估"引全量库"vs"继续增强 SVG" |
| 2 | SVG token 实现方式未说明 | 写"fill 取 var()" | SVG 属性 fill 不支持 var()，必须 style 内联或 CSS 类；现状硬编码 fill 需改造 |

| 4 | spec 升级缺向后兼容 | 未提 | renderBoardContent 双形态识别（spec 优先，回退 text）；旧数据按需升级不一次性迁移 |

| 6 | Phase 2 工期严重低估 | 5d 塞编辑器+库+模板+拖拽 | 拆 2a（spec+库 3d）/ 2b（编辑器+模板+拖拽 4d），编辑器单独 |

### 5.2 推荐落地方式（对齐现状，可立即执行）

**立即可做（Phase 1，零依赖，3d）——按以下顺序，每步独立可验证：**

1. **配色 token 化（0.5d）**：在 `:root` 加 `--viz-*` 变量；把 `renderBarChart/LineChart/PieChart` 的硬编码 `fill="#378ADD"` 改为 `style="fill:var(--viz-primary)"`（注意是 style 不是 attr）；饼图 8 色数组改为读取 `--viz-categorical` 拆分。验证：浅色/深色切换图表跟随。
2. **SVG 图表增强（1d）**：柱/折线补 Y 轴刻度线 + 网格虚线 + 图例；饼图标签防溢出（标签外置 + leader 线）。复用现有 `renderChart` 函数，不动 ` ```chart ` 协议。
3. **hover + 入场动画（0.5d）**：`.kv-card:hover` 抬升+阴影+边框聚焦色；柱 `@keyframes` 从 0 升起、折线 `stroke-dasharray` 绘入；`IntersectionObserver` 卡片淡入。
4. **响应式断点（1d）**：`@media` 宫格 3/2/1 列；1 列时取消固定"更多+"改底部"查看全部"；预览层 768px 下全屏模态。

**中期（Phase 2，分两步）——先结构后编排：**

- **2a spec 结构化 + 富图表评估（3d）**：先不引库，把 boardView 升 spec（双形态兼容）；评估"引全量 ECharts UMD 1MB"是否值得（桌面端内联 1MB 可接受，网页端首屏增 1MB 需权衡）——若不值得，继续增强 SVG（加 radar/funnel）。
- **2b 编辑器 + 模板 + 拖拽（4d）**：可视化编辑器（类型/配色/字段）+ 模板库 + Gridstack 自定义布局。

**远期（Phase 3）——务实优先：**
- 近期用"定时任务更新发布"模拟刷新（复用 publishVersion，零后端改动）。
- 真订阅刷新需新增 CloudRun 服务，列远期单独评估，不与看板美化耦合。

### 5.3 需你拍板的关键决策

1. **中期是否接受引全量 ECharts UMD**（网页端首屏 +1MB）？还是继续深耕 SVG（加 radar/funnel/metric）？
2. **可视化编辑器是否本轮必须**？还是先靠 agent 产出 + schema 兜底 + 用户微调？
